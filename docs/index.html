# overview

why this exists, and what it actually does

problem.md

Database work splits awkwardly across tools. A GUI client runs queries but forgets why you ran them. A notebook documents reasoning beautifully but needs a driver, a kernel and a pile of glue before it can touch a real database — and a different pile again for MongoDB.

Neither remembers what the team ran last week, and neither has an answer for "who has the production password?"

solution.md

One browser workspace. Saved connections with credentials encrypted at rest, a schema tree introspected live from the target database, SQL and Markdown cells side by side, and every execution logged with its duration, row count and error.

Roles decide who sees what: users get their own notebooks, admins get platform analytics and the global audit log.

# query_lifecycle

what happens between pressing Ctrl+Enter and seeing rows

or click any step

Cell submits to the API

The cell's SQL text and the selected connection_id are POSTed to /api/v1/query/execute with the JWT in the Authorization header. Nothing about the target database is trusted from the browser beyond that id.

Token decode & role check

A FastAPI dependency decodes the bearer token with python-jose, loads the user, and rejects the request before any handler runs. Admin-only routes carry an extra role guard, so an ordinary user can never reach the global audit log.

Connection resolved & decrypted

The connection row is loaded from the app store and its password is decrypted in memory with Fernet. Plaintext credentials exist only for the life of the request — they are never returned to the client, and never written to a log line.

Driver dispatch

The connection's engine picks the connector: asyncpg, aiomysql, aiosqlite or motor. All four sit behind one base interface, so the route above them doesn't branch. MongoDB takes a structured JSON command object where the relational engines take SQL.

Execution, timed and guarded

The query runs asynchronously against the target database while a timer measures wall-clock duration. A single-statement guard rejects batched statements in one cell — it keeps the cell / result mapping honest, and it is exactly the kind of error you can see captured in the history panel screenshot below.

Audit record written

Success or failure, the run is persisted: query text, engine, duration in milliseconds, row count, status and error message. That single table backs both the user's history panel and the admin audit log — one write, two very different views.

Rows render, history refreshes

Columns and rows come back as JSON, the cell renders its result grid with the execution time in the header, and the history drawer picks up the new entry with copy and re-run actions attached.

# what_it_does

the feature set, honestly summarised

⌨️

Cell-based execution

SQL and Markdown cells with Monaco, syntax highlighting, Ctrl+Enter to run, per-cell timers, and Run All for the whole notebook.

🔌

Four engines, one interface

Native async connectors for PostgreSQL, MySQL, SQLite and MongoDB behind a shared base class.

🌲

Live schema explorer

Tables, collections, views, primary keys and column types introspected from the real database — click to copy a name into the editor.

🕓

History & auditing

Every run logged with duration, rows and diagnostics. Copy or re-insert any past query in one click.

🛡️

RBAC + admin analytics

User vs admin roles, user management, activation toggles, and a platform dashboard with success rate and average query time.

🔐

Credentials encrypted at rest

Connection passwords sealed with Fernet (AES-128-CBC + HMAC-SHA256) before they ever touch storage.

🎓

In-app learning hub

Guided tutorials per engine with per-section progress tracking, so a new user has something to run on day one.

🐳

One-command stack

⚙️

CI/CD pipeline

GitHub Actions runs ruff, pytest against a live PostgreSQL service, tsc, a Next build and Docker image verification.

# security_model

the part that decides whether anyone would actually run this

🔑

Authentication

Stateless JWT bearer tokens signed with HS256; passwords hashed with bcrypt. Token lifetime is configurable and defaults to 24 hours.

🧱

Authorization

Two hierarchical roles — user and admin — enforced by route-level dependencies rather than checks scattered through handlers.

🗝️

Credentials at rest

Fernet symmetric encryption (AES-128-CBC with HMAC-SHA256 authentication) over every stored database password and connection string.

🧯

Query isolation

User queries run through isolated async driver interfaces against the target database, never through the application's own ORM session.

# run_it_yourself

the whole stack in one command

// option 1 — docker compose

# clone and start every service
git clone https://github.com/itz-Maheshkumar/Collaborative_Database_Notebook.git
cd Collaborative_Database_Notebook
docker compose up --build

# frontend  → http://localhost:3000
# api       → http://localhost:8000
# api docs  → http://localhost:8000/docs

// option 2 — local dev

# backend
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --reload --port 8000

# frontend
cd frontend
npm install
npm run dev

# engineering_notes

decisions worth defending in an interview

Async all the way down

Every driver is an async one, so a slow analytical query on PostgreSQL doesn't block the event loop for the person running a fast lookup on SQLite. FastAPI + SQLAlchemy 2.0's asyncio layer made that the default rather than an optimisation.

Encryption, not hashing, for connection secrets

User passwords are hashed with bcrypt because they only ever need verifying. Database credentials must be replayed to the target server, so they are encrypted with Fernet instead — a genuinely different requirement that deserves a different primitive.

One connector interface, four engines

A shared base class keeps engine-specific quirks inside each connector. Adding a fifth engine means writing one class, not touching the query route, the history model or the UI.

One audit table, two products

The same execution log powers the user's personal history drawer and the admin's platform analytics. Aggregation happens at read time, so the write path stays a single insert.

A single statement per cell

Rejecting batched statements keeps the cell → result mapping unambiguous and makes durations meaningful. It surfaces as a clean error in the history panel rather than a silently partial run.

Docs as part of the build

FastAPI's generated OpenAPI schema means the API surface can't drift from the code, and CI verifies the Docker images build — so "it works on my machine" isn't a valid defence.
